# 题迹架构审查与冗余优化

## 结论与范围

当前项目具备分层基础，主要问题是边界没有被工程结构约束，多个大文件同时负责 UI、状态协调、持久化与外部请求。适合逐条业务链收敛，不适合整体重写。

本轮遍历自有 Kotlin 源文件、检查构建与 CI、审阅核心调用链；不包含逐行审计全部第三方 PaddleOCR 源码，不宣称完成安全审计或手机性能测量。审查开始时自有生产代码为 163 个 Kotlin 文件、35,429 行：data 19 个、domain 16 个、service 41 个、ui 86 个，另有 MainActivity。测试目录含 39 个 JVM 测试文件、59 个 Android 测试文件；文件数量不代表覆盖率。本轮新增的测试另计。

工作区已有大量此前改动，本轮保留它们；没有 reset、批量删除或把既有改动当成本轮成果。

## 当前结构

| 层/链路 | 当前实现 | 评价 |
| --- | --- | --- |
| 工程模块 | `settings.gradle.kts`：app + 本地 paddleocr SDK | 足够支撑单应用；暂不必为了分层拆几十个 Gradle 模块 |
| 持久化 | Room 数据库 v12、DAO、MistakeRepository；偏好及任务存储 | Room 迁移、事务基础明确；任务状态事实来源比较分散 |
| 领域规则 | 复习调度、每日计划、知识点、草稿与资产管理 | 应继续保留纯规则和测试，不把算法塞回页面 |
| UI 与导航 | Compose → TijiApp → TijiNavGraph → 各页面，共享 MistakeViewModel | 根页面订阅过多；功能之间的生命周期和重算边界不够独立 |
| AI | 解题、追问、识别、分类前台 Service → 协议/网络服务 → 持久化状态 → ViewModel | 后台任务可恢复是优点；轮询及重复状态映射增加维护成本 |
| 图像/OCR | 相机与相册 → 私有文件 → 图片处理；OCR 独立进程 | 隔离 OCR 有价值；UI 层多处承担媒体流程，容易漏状态恢复 |
| 公式与打印 | MathText/WebView 池；列表预览内存/磁盘缓存；HtmlPdfExportService | 有限额与按题失效机制；屏幕/PDF 排版实现重复，回归风险较高 |
| 备份 | BackupService + 持久化恢复标记、文件提交机制 | 不应作为“冗余”删除恢复与兼容分支 |

数据库证据：`data/AppDatabase.kt:10` 声明 v12 与 schema 导出，`:38` 使用显式迁移；未用破坏性迁移回退。缓存证据：`ui/math/MathSnapshotMemoryCache.kt` 上限 20 MiB，`MathSnapshotDiskCache.kt` 上限 128 MiB，并有 owner/generation 失效校验。CI：`.github/workflows/android.yml` 包含编译、JVM 测试、lint、打包及 API 30 设备测试；本轮没有查询远程 CI 当前结果。

## 本轮已实施

1. **移除不再被读取的三天预测计算链。** 原 `TijiApp.kt` 计算 `latestReviewRecordByMistake` 和 `FutureReviewPlan.calculate(days=3)`，再写入 `TijiNavGraphState.futureReviewPlan`；全 UI 搜索只有构造和声明，没有读取端。移除根页面计算、分组及导航参数。今日计划、“接下来的题”、日历功能不变；领域算法本身保留。减少每次相关数据变化时无用的主线程计算，具体节省时间尚未测量。
2. **合并三处题图追加逻辑。** 在 `QuestionContentBlockCodec.appendQuestionImages` 统一现有图片最大 order + 1、生成 QUESTION 图片块的逻辑。AI 解题、录题编辑、详情编辑使用同一实现。各调用方原有去重策略、已有块顺序/元数据、持久化行为不变。
3. **移除 20 条无用导入。** 限于最近抽取图片来源弹窗后残留的 `PhotoEditFields.kt`、`AddQuestionImagesButton.kt` 显式 UI 导入，不执行全工程不可靠的“未使用代码删除”。

## 需要改进的项目，按优先级排序

### P1：后台任务观察改为状态通知，避免主线程持续轮询完整数据

证据：`ui/MistakeViewModel.kt` 的 `observeAiMistakeSave` 用 `viewModelScope.launch` 每 250 ms 调用 `latestForUi`，即使无活动任务也一直循环；`service/AiMistakeSaveStore.kt:77` 的 `latestForUi` 会 `readAll()` 并查找最新任务。解题、追问、识别各自也有 250 ms 轮询。`AiSolveStateStore.read` 会读取正文文件，`DurableTextStore.read` 为同步文件读取。

影响：可以静态确认有重复读取/解析；是否为当前手机卡顿主因需要 trace，不能仅凭源码下结论。

改进：先把持久化作为唯一恢复来源，增加进程内 Flow 状态发布和启动时的一次恢复；跨进程的 OCR 链路保留合适的 IPC/通知机制。过渡期把读取移到 IO，停止空闲轮询。必须验证进程死亡、任务完成后返回、取消与重复提交，不能简单删掉轮询导致丢结果。

### P1：按业务拆分 ViewModel 和根页面状态

证据：主 ViewModel 初始 1,800 行，自己创建数据库、Repository、偏好和多种任务 Store；`TijiApp.kt` 同时订阅全量错题、查询结果、历史记录、知识点、偏好，并在组合阶段计算今日计划。`TijiNavGraphState` 把大量互不相关的数据和各页滚动状态集中传递。

改进：先抽 `AiTaskCoordinator` 和 `ReviewCoordinator`，再让错题库、复习、解题按页面订阅各自 UiState；根页面保留导航、主题、全局反馈。首次拆分不改变存储格式和任务所有权。Repository/时钟/任务观察通过构造参数注入，方便确定性测试。无需立刻引入新的 DI 框架。

### P1：题目、识别结果、历史和已保存错题之间建立明确同步契约

证据：AI 追加图片同时更新 solve 状态、任务存储、历史、已保存错题；录题有 domain 草稿绑定，详情还有独立 Compose 字段。前几轮的“填入不切换模式”“文字录题图片未保存”正发生在这些边界。

改进：统一 Draft/Attachment 的增删、结果填入、保存转换，由一个用例完成；UI 只提交动作。以“显示内容 = 保存内容”“图片新增/删除后的持久化”和“取消不会删仍被引用图片”作为契约测试，而非仅测试按钮存在。

### P2：拆分 AI 协议大文件，但保留现有兼容层

证据：`service/AiVisionService.kt` 初始 2,628 行，含 HTTP transport、流响应、提示词、结构化解析、识别修复与视觉辅助。已有 transport 接口，具备拆分起点。

改进：逐步分为 transport、流解码、solution/recognition codecs、prompts、orchestrator。保持不同服务商的正常响应、截断、非 V2、公式与 reasoning 字段样本回归。没有证据的兼容分支不能因为看着重复就删除。

### P2：按需查询，减少全量历史与完整题目的常驻派生

证据：`MistakeDao.observeActive` 返回全量实体；根页面收集 `allMistakes` 和 `allReviewRecords`；数据库变化可能触发列表索引和统计重新派生。现有 `LibraryIndex` 已用 `mapLatest + Dispatchers.Default`，这部分方向正确。

改进：保留完整题目展示要求，先将计数、近期记录、知识点统计改成页面需要时订阅；用大数据集测量后再决定是否 Paging。先测 100/1,000/5,000 道题的查询、首次展示、返回滚动位置和内存，不预设“换分页就一定更快”。

### P2：统一数学内容解析，分离屏幕与纸张布局

证据：`MathHtmlBuilder` 和 `HtmlPdfExportService` 都处理公式定界、标点和显示结构，后者初始 1,218 行。复用 HTML/CSS 整体并不合适，纸张有分页、物理尺寸、作答区要求。

改进：共享保守的源文本规范化/内容块解析，屏幕和 PDF 各自布局。保留当前有界缓存及按题清理；为宽度、字号、主题、图片变化建立缓存键和失效测试。禁止以缓存替代根因分析或退回未完成渲染截图。

### P2：增加性能证据，整理测试与交付追踪

现有测试覆盖迁移、备份恢复、AI 协议和 UI，但本轮未运行全套，也没有实际性能基线。建议记录任务首字延迟、协议解析耗时、列表渲染次数、滚动帧时间和内存峰值。指标不包含密钥或完整题目敏感内容。

`app/build.gradle.kts` 当前 versionCode 114、versionName 1.0.0；连续发布使用同名 APK，验收不易区分。建议保留可追踪构建号、源码版本和哈希，并把工作区多轮修改按独立行为拆成可审查提交。签名延续和发布门禁不能在本轮审查中擅自更换。

## 建议实施顺序

无消费者计算与纯函数去重（本轮） → 任务存储观察/线程隔离 → 录题资产用例与契约测试 → ViewModel 分责 → 全量查询与性能基线 → AI/数学解析文件拆分。

不要同时改任务持久化、渲染方式、数据库格式和 UI；每一步保留 API 30 回归与可定位的变更范围。
