# 题迹架构改进：AI 任务状态通知

日期：2026-09-29

## 本轮解决的问题

`MistakeViewModel` 原有四条 250 ms 轮询：解题、追问、识别、保存/分类。保存状态在无任务时仍每秒读取约四次任务列表；解题和追问读取包含正文文件。这些观察器原来在主线程协程中同步读取。

本轮将它们改为写入后通知，读取在 IO 线程执行。没有改变模型请求、解题内容、题卡渲染、数据库格式和已有文件持久化协议。

## 实现

- 新增 `service/TaskStateUpdates.kt`：每种 Store 一个进程内版本号 StateFlow；订阅立即读取当前持久化状态，版本变化后重新读取。去重与合并避免 UI 排队处理已经过期的状态。
- 四种 Store 在 write/upsert 和 clear 完成后发通知；各自提供 `observe()`。
- ViewModel 用 Flow 接收状态。解题、追问、识别只处理当前 requestId，包含终态在内，处理完终态自动停止观察。保存状态随 ViewModel 生命周期观察，无定时唤醒。
- 保留复习时钟的定时刷新，因为它需要在时间变化时更新。
- 通知只传版本号，不长期缓存正文副本。当前生产代码只有四种固定 Store key。

为什么不只用 SharedPreferences 监听：追问正文写在独立文件中，文字变化时 Preferences 中的元数据可能完全不变。显式写后通知覆盖这种情况。

为什么恢复仍然有效：通知不是结果的唯一存储；每个新订阅先读取持久化状态。订阅之前已完成的结果也会返回。OCR 的独立进程不使用此通知总线，原跨进程链路保持原状。

## 边界和下一步

本轮消除了可从代码确认的重复轮询，没有测得手机帧率提升比例，也没有进行真实杀进程或远端模型请求测试。持久化格式不变不等于已完成所有恢复场景验收。

ViewModel 冷启动的部分一次性同步读取、历史记录同步写入、录题草稿同步契约、按页面查询和大型文件分责仍需分批改进。避免同时替换持久化、渲染和导航，导致回归无法定位。

本轮不推送工作区累计的无关修改。
